## 3. Architecture decisions (follow these)

**Rule: Python decides, Gemini explains.**
- Python (deterministic): available hours, deadline maths, time blocks, scoring, choosing the recommendation.
- Gemini: parses free-text input and feedback into structured JSON, and writes the "why" explanations.
- **Memory drives scoring.** Each stored memory has a key and value, and the scoring function reads them. When feedback changes `task_order` from `exam_first` to `assignment_first`, the score changes and the recommendation flips for a real, explainable reason, not because the LLM felt like it.
- **Fallback:** if Gemini fails, times out or has no key, use keyword rules to parse feedback and templated text to explain results. The demo must never break.
- Check the current recommended Gemini Flash model name in the official docs, and put it in `.env` as `GEMINI_MODEL`.

**One Flask app and one React app.** The six layers are modules, not services:

| Layer | Where it lives |
|---|---|
| 1 Twin Identity | `memories` table + `services/twin.py` |
| 2 Context & Behaviour Engine | `services/context.py` |
| 3 Parallel Reality Simulator | `services/simulator.py` |
| 4 Twin Evolution | `/api/feedback` + `memory_history` table |
| 5 Privacy Control Centre | `permissions` table + memory filtering |
| 6 Confidence & Evidence | `services/confidence.py` (rule-based High / Medium / Low with reasons) |

**Database (SQLite):**

```sql
CREATE TABLE profile (
  id INTEGER PRIMARY KEY, name TEXT, course TEXT,
  goals TEXT,                -- JSON list
  daily_hours_available REAL, focus_style TEXT
);
CREATE TABLE memories (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  key TEXT,                  -- e.g. task_order, session_style
  value TEXT,                -- e.g. assignment_first, focused_blocks
  category TEXT,             -- preference | routine | goal | decision
  label TEXT,                -- human-readable sentence shown in UI
  source TEXT,               -- initial | feedback | user_edit
  active INTEGER DEFAULT 1,
  updated_at TEXT
);
CREATE TABLE memory_history (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  memory_key TEXT, old_value TEXT, new_value TEXT,
  reason TEXT, created_at TEXT
);
CREATE TABLE permissions (
  category TEXT PRIMARY KEY, allowed INTEGER DEFAULT 1
);
CREATE TABLE tasks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT, type TEXT,     -- exam | assignment
  due_at TEXT, est_hours REAL, done INTEGER DEFAULT 0
);
CREATE TABLE scenarios (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  question TEXT, created_at TEXT
);
CREATE TABLE scenario_runs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  scenario_id INTEGER, result_json TEXT,
  memory_snapshot TEXT,      -- JSON of memories used in this run
  created_at TEXT
);
CREATE TABLE feedback (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  scenario_id INTEGER, text TEXT, parsed_json TEXT, created_at TEXT
);
```

`memory_snapshot` and `memory_history` are what make the evolution demo visible: Run 1 vs Run 2, with the exact memory change between them.

**API (all under `/api`):**

| Method | Endpoint | Purpose |
|---|---|---|
| GET | /health | Health check |
| POST | /profile | Create or update profile |
| GET | /twin | Profile + active memories + tasks + evolution level |
| POST | /scenario | Generate and compare scenarios (A/B), recommendation, confidence, evidence |
| POST | /feedback | Parse feedback, update memory, write history, **automatically rerun the scenario**, and return both the old and new runs |
| GET | /memory | List memories |
| PATCH | /memory/<id> | Edit a memory |
| DELETE | /memory | Delete selected (`?id=`) or all memories |
| GET/PATCH | /permissions | Read or toggle permissions per category |
| POST | /reset | Reset the twin back to seed data |

**Data flow for the demo loop:**
1. `GET /twin` loads the profile, memories and tasks.
2. `POST /scenario {question}` filters memories by permissions, computes hours, builds plans A and B, scores them with memory weights, asks Gemini for explanations, then returns realities, recommendation, confidence and evidence.
3. `POST /feedback {scenario_id, text}`: Gemini extracts e.g. `{key: "task_order", value: "assignment_first"}`, the memory is updated, a history row is written, the scenario reruns, and the response contains the old run and the new run.
4. The Evolution page shows the memory diff plus the old vs new recommendation.
5. Privacy page: view, edit and delete memories, toggle permissions, reset.

# PROJECT: ALTER EGO: AI-Powered Digital Twin

Act as an experienced full-stack developer, AI engineer, UI/UX designer, and hackathon mentor. Help me build a working, impressive prototype of **ALTER EGO** for a 24-hour hackathon.

## 4.1 Project Identity

**Project Name:** ALTER EGO
**Tagline:** Your Life. Your Choices. Your Parallel Realities.

**Concept:**

ALTER EGO is an AI-powered digital twin that learns about an individual through their permitted preferences, routines, goals, historical decisions, and feedback.

It understands the user's current circumstances, identifies patterns, simulates alternative scenarios, and provides personalised decision support.

Unlike a conventional chatbot that answers individual prompts, ALTER EGO builds an evolving representation of the person. It learns from corrections and real-life feedback, allowing its understanding and recommendations to improve over time.

The user remains in control of their personal information through privacy settings, memory visibility, and data deletion.

## 4.2 Problem Understanding

Every decision shapes a different possibility, yet we rarely get to see where our choices might lead us.

Existing digital assistants often provide generic advice but lack a deeper understanding of an individual's habits, goals, and changing circumstances.

People need more than answers: they need an AI that understands them, explores possible outcomes, and evolves with their experiences.

**ALTER EGO bridges this gap by creating a personalised digital twin that learns, simulates alternate realities, and helps individuals make informed decisions while keeping their personal data under their control.**

## 4.3 Proposed Solution

ALTER EGO creates a personalised digital representation of an individual using permitted personal information.

It combines contextual awareness and behavioural intelligence to:

* Understand the user's goals, habits, preferences, and routines.
* Analyse their current situation, workload, deadlines, and constraints.
* Simulate multiple what-if scenarios.
* Compare potential outcomes, risks, and trade-offs.
* Provide personalised recommendations with explanations.
* Learn from user corrections and feedback.
* Give users control over their data and stored memories.

The system should not present hypothetical outcomes as guaranteed predictions. It should clearly communicate assumptions, uncertainty, and limitations.

## 4.4 Six-Layer System Architecture

Build the project around these six interconnected layers:

### Layer 1: Twin Identity

Creates the user's digital profile from permitted information:

* Personal preferences
* Goals and priorities
* Daily routines
* Learning or working style
* Historical decisions
* User-provided behavioural patterns

The twin should have editable memory that the user can inspect and correct.

### Layer 2: Context & Behaviour Engine

Analyses the user's current situation:

* Schedule and available time
* Deadlines and tasks
* Workload
* Priorities
* Dependencies and conflicts
* Behavioural patterns

It combines the user's profile with their present circumstances.

### Layer 3: Parallel Reality Simulator

This is the main feature of ALTER EGO.

It allows users to explore different decisions through what-if scenarios.

For example:
"What if I study for my exam first instead of completing my assignment?"

The simulator should:

* Generate alternative plans or scenarios.
* Compare their possible outcomes.
* Identify risks and trade-offs.
* Explain how each scenario aligns with the user's goals.
* Display a personalised recommendation.

Use deterministic calculations for factual values such as available hours and deadlines. Use AI to interpret the situation and explain the results. Do not rely entirely on an LLM to invent calculations or predictions.

### Layer 4: Twin Evolution

The twin should continuously adapt through:

* User corrections
* Feedback
* Updated preferences
* Changes in routines or goals
* Actual outcomes, when provided by the user

The system must visibly demonstrate that feedback changes the twin's stored understanding and can influence future recommendations.

### Layer 5: Privacy Control Centre

Users should have control over their personal data.

Include:

* Permission controls for information the twin can use.
* A view of stored memories.
* Ability to edit or delete memories.
* Ability to reset the twin.
* Clear indication of what information is being used.

For the hackathon, use fictional sample data unless the user explicitly provides their own information.

### Layer 6: Confidence & Evidence Layer

Recommendations should be transparent.

Show:

* Why a recommendation was generated.
* Which user preferences or contextual details influenced it.
* Assumptions made.
* Missing information.
* Qualitative confidence levels such as High, Medium, or Low, with an explanation.

Do not display arbitrary confidence percentages.

## 4.5 Main Demonstration Scenario

The main demo should use a fictional student profile.

**Sample user situation:**

A student has:

* An exam tomorrow.
* An assignment due tonight.
* Limited available time.
* A preference for studying in focused sessions.

The student asks:

"I have an exam tomorrow and an assignment due tonight. What should I prioritise?"

### Initial Twin Response

The twin analyses the profile and current situation, then generates two possible plans:

**Reality A:** Prioritise exam preparation first.
**Reality B:** Complete the assignment first, then study.

Display a side-by-side comparison of:

* Time allocation
* Task completion
* Workload
* Potential risks
* Alignment with the user's preferences

The twin then provides a recommendation with reasoning.

### The Important Feedback Moment

The user corrects the twin:

"I usually finish assignments first because unfinished work distracts me."

ALTER EGO should then:

1. Understand the correction.
2. Update the user's stored behavioural preference.
3. Display the updated memory.
4. Rerun the same scenario.
5. Show how the recommendation changes because of the new information.

This visible feedback loop is the project's most important demonstration. Make it clear that the twin is evolving, not simply generating another chatbot response.

**Note for the seed data:** the initial memory should say the student prefers `exam_first`, so the first recommendation is Reality A. After the correction, the memory becomes `assignment_first` and the recommendation flips to Reality B.
